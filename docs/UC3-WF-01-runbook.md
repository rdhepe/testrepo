## Test basis and limits

The provided UC3-WF-01 screenshot specifies assessment creation, attachment
linkage, metadata and repository preservation, invalid-input validation, reopening,
and evidence capture across 26 steps. This pack provides a sample application and
matching documents; perform the actual workflow in your existing UC3 application.

The screenshot does not enumerate mandatory metadata fields, exact labels,
supported document types, size limits or approved repository-reference rules.
Confirm those rules before judging results. Metadata mapping and PDF/DOCX formats
are proposed inputs, not assertions about UC3's schema or allowlist.

## Positive workflow

1. Confirm approved rules, authorized access and prepared inputs (steps 1 to 3).
2. Sign in, open assessment management and create a new assessment (steps 4 to 6).
3. Enter mapped metadata, attach one HLD and one DPIA, and enter the repository URL (steps 7 to 10).
4. Review the values and submit (steps 11 to 12).
5. Capture the success response and unique UC3 assessment ID (step 13).
6. Open that assessment and compare every entered field with the saved values (steps 14 to 15).
7. Verify both documents belong to that assessment, open them and compare their contents (steps 16 to 17).
8. Compare the saved repository reference with the submitted value (step 18).
9. Refresh or reopen the successful assessment and repeat metadata, attachment-access and repository checks (steps 23 to 24).

Record each chosen filename, format, size and manifest checksum. If UC3 permits
attachment downloads, compare the downloaded checksum. If it only offers previews,
capture the visible document ID and content instead.

## Negative inputs

For steps 19 to 22, start separate assessment attempts. Change only one input at a
time, keeping the rest valid. The `negative` folder supplies one omitted metadata
field per file, an invalid email, an invalid repository and an invalid metadata
type. Treat a missing field as an error only if approved rules require it. The
object-valued name variant applies only if the UI or supported API permits it;
otherwise record it as not applicable.

Test missing HLD and missing DPIA separately if mandatory. The file
`unsupported-upload.exe` is inert plain text, not executable software. Confirm that
extension is disallowed before expecting rejection. `corrupt-document.pdf` is
deliberately not a valid PDF; compare UC3's response with approved content rules.

Expected behavior for required missing or invalid values is validation feedback
and no created assessment. Check the assessment list for unintended creation;
an error banner alone is insufficient. Verify the earlier successful assessment
and attachments remain unchanged after failed attempts.

## Evidence and defects

Copy either evidence template to an ignored `test-results` directory for each run.
Retain the source template so new runs start at `NOT_RUN`. Record environment,
assessor, approved-rule reference, repository approval, actual repository URL,
UC3 assessment ID, screenshots, document references, actual results and defects.
Assign PASS, FAIL, BLOCKED or NOT_APPLICABLE only after observing the step.

Steps 25 and 26 require assessment details, validation messages, document and
repository references, and expected versus actual behavior for defects. The
templates include one row per screenshot step. No UC3 test is executed by building
this pack, and no UC3 result is inferred from the local fixture tests.
