## Quick capture checklist

Upload the shared [DPIA.pdf](../test-data/uc3-wf-01/documents/DPIA.pdf) to UC3, run document
analysis, and compare the extracted results with every row below. You do not need
to start the sample API. Do not upload the reference answers or comparison files.
If UC3 requires other assessment inputs, supply the WF-01 HLD and repository, but
check DPIA extraction against this uploaded DPIA only.

| Check in UC3's extracted output | Expected result | DPIA PDF page |
| --- | --- | --- |
| Data subjects | Fictional employees enrolled as learners; no invented customer or patient groups | 2 |
| Identification fields | Both `employeeId` and `employeeName` | 3 |
| Contact field | `workEmail` | 3 |
| Learning fields | Both `courseCode` and `completionStatus`, recognized as personal information when linked to an employee | 3 |
| Generated identifier | `id`, generated by the application for new records only; seed records have no `id` | 3 |
| Four categories | Employee identification data; contact data; learning data linked to an employee; record identification data | 3 |
| Metadata distinction | `ownerEmail` is an application business contact, not a learner enrolment field | 3 |
| Excluded enrolment fields | No passwords, national IDs, IP addresses, authentication tokens, health data or financial data reported as collected | 3 |
| Two purposes | Register employees for training; track course completion | 4 |
| Excluded uses | No implemented email sending, marketing, profiling or automated decisions | 4 |
| Collection and use | Local client submits five fields; Node.js validates them, generates `id`, stores the record in memory and returns it | 5 |
| Access and recipients | Local tester is intended recipient, but any local client can read records without authentication; access is not identity-enforced | 5 |
| Repository disclosure | Publishing exposes synthetic seed data and documents according to repository visibility | 5 |
| Persistent storage | Two seed enrolments in the local seed JSON file remain until manually removed | 6 |
| Temporary storage | Runtime enrolments are in Node.js process memory and are lost on restart; seed file stays unchanged | 6 |
| Absent infrastructure and controls | No implemented database, cloud deployment, backup, cross-border transfer or automated retention/deletion | 6 |
| Missing country | Not specified; UC3 must not guess a country | 7 |
| Missing seed retention duration | Not specified; UC3 must not invent a number of days or years | 7 |
| Missing repository visibility | Not specified in the DPIA; UC3 must not claim public or private based on this document | 7 |
| Future partner export | Ambiguous future proposal, not current sharing or an approved purpose; partner, fields, destination and timing are undecided | 7 |
| Privacy statement requirement | Required homepage link before submission, readable without authentication; not an assertion of implementation | 8 |
| Consent requirement | Consent required before submission and storage for the synthetic scenario; not an assertion of implementation or valid consent | 9 |
| Citations | Each extracted fact has a source reference that opens supporting content, not merely an unrelated page | 2-9 |

Accept different wording when the meaning matches. Record a discrepancy for each
missing expected fact, incorrect statement, invented detail or missing/incorrect
citation. Check any extra UC3 claims against the source too. For example, claiming
that the app emails learners or retains records for seven years is incorrect.

Use [comparison-template.csv](../test-data/uc3-doc-01/comparison-template.csv) to
record actual values and citations against individual reference facts. Use
[run-evidence-template.csv](../test-data/uc3-doc-01/run-evidence-template.csv) for
the 25 execution steps, screenshots and defects. Local test results do not prove
that UC3 passed. Formal sign-off still requires the approval described below.

## Scope and approval

UC3-DOC-01 checks extraction of personal-data categories and purposes from a DPIA,
including fields, subjects, storage, processing activities and supporting citations.
This pack follows the 25 steps in the supplied test-case screenshot. It is not a
UC3 implementation, an automated extraction result, or an SME-approved DPIA.

The shared DPIA contains the baseline inventory and synthetic control requirements.
Deliberate code/document mismatches support the privacy negative tests; DOC-01
extraction is evaluated against the uploaded document, not assumed code behavior.
Real personal data is neither required nor permitted. Running the API is optional.

1. Generate the shared documents and both packs with `npm run pack:all`.
2. Ask your SME to review the exact DPIA and reference annotations for completeness
   and accuracy. Record approval and any required revisions outside the repository.
3. If revisions are needed, update [the source fixture](../fixtures/doc-01.json),
   regenerate and obtain approval again. Regeneration invalidates previous file hashes.
4. Record the approved PDF or DOCX hash from [the manifest](../test-data/uc3-doc-01/manifest.json).
   Record the approved annotation hash using `Get-FileHash` with SHA256. The generated
   `PENDING_SME_REVIEW` state is intentional; a tester records real approval in their
   run evidence, not by claiming that the generator obtained it.
5. Confirm authorized UC3 access, allowed upload formats and size limits. If SME
   approval is unavailable, exploratory testing is possible, but the approved-case
   prerequisite remains BLOCKED.

* Upload [DPIA.pdf](../test-data/uc3-wf-01/documents/DPIA.pdf), or the DOCX alternative if UC3 supports it. Use one format per run.

* If UC3 requires an HLD, use the shared [HLD.pdf](../test-data/uc3-wf-01/documents/HLD.pdf). Use the same document pair across all implemented cases; count only assertions supported by the uploaded DPIA for extraction.

The PDF has a cover followed by one section per page. For DOCX, use headings and
quotes rather than assuming a fixed page number across Word renderers.

| Section | PDF page | Reference coverage |
| --- | --- | --- |
| S1 | 2 | Fictional employee/learner subjects |
| S2 | 3 | Four categories, six enrolment fields, metadata contact and excluded data |
| S3 | 4 | Registration and completion purposes; excluded uses |
| S4 | 5 | Collection, generated ID, use, access and synthetic repository disclosure |
| S5 | 6 | Persistent seed JSON versus volatile process memory and absent controls |
| S6 | 7 | Three unspecified details and an ambiguous future proposal |
| S7 | 8 | Required user-facing privacy statement, not an implementation claim |
| S8 | 9 | Synthetic consent prerequisite, not proof of actual valid consent |

Category labels may differ if meaning is preserved. `courseCode` and
`completionStatus` are personal information when linked to an employee, although
they are not identifying in isolation. `id` exists only on newly created records;
`ownerEmail` is a metadata contact, not a collected learner field. The declared
future export is not implemented sharing or an approved processing purpose.

## Execute and capture evidence

1. Create a private run folder under ignored `test-results` and work from copies
   of the [JSON evidence template](../test-data/uc3-doc-01/run-evidence-template.json)
   or [CSV evidence template](../test-data/uc3-doc-01/run-evidence-template.csv).
2. Record assessor, environment, assessment ID, approval reference, approved file
   hashes and the exact uploaded document format. Execute all 25 numbered actions.
3. Upload the approved DPIA and run UC3 document analysis. Capture workflow status
   and the original extracted output before reviewing it against the answer set.
4. Fill the comparison worksheet with actual extraction and UC3 citation for each
   reference item. Check that citations open the correct source section or quote.
   Equivalent paraphrases are acceptable; a page number alone does not establish
   that a citation supports the claim.
5. Check every additional UC3 assertion against the DPIA, not only the listed
   references. Record unsupported additions, material omissions, incorrect values
   and absent or incorrect citations as defects with expected versus actual results.
6. Confirm that UC3 identifies the missing country, fixed seed retention period
   and repository visibility without inventing values. The undecided partner,
   export fields, destination and timing must remain unknown or ambiguous, not be
   represented as current processing. A missing duration is distinct from the
   explicit statement that runtime records are lost on restart.
7. Preserve annotations, extracted output, citations, screenshots and discrepancy
   details. Ask the SME to review fidelity and record PASS, FAIL or BLOCKED based
   on observed results and your approved acceptance criteria.

Do not upload reference answers to make the extraction appear correct. Do not
mark steps passed from local tests or hashes: actual UC3 execution is required.
